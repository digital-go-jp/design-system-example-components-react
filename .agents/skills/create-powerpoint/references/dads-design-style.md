# DADS PowerPointデザインスタイル手順書（React版）

この手順書は、DADSのReact実装をPowerPointへ静的に変換するときの既定ルールである。個別のコンポーネントを再現する場合は、必ず対象の `<Name>.tsx`、`<Name>.stories.tsx`、`<Name>.mdx`、`component-spec.md` を一次情報として優先する。

## 1. 作成前の確認

1. 資料の目的、対象読者、スライド構成、出力先を確認する。
2. `node_modules/@digital-go-jp/design-tokens/dist/tokens.css`（`npm install` 後に存在）、対象コンポーネントのソース、関連するFoundationドキュメント（`src/foundations/`）から使用値を抽出する。
3. 一般資料はこの手順書のテンプレート規則を使用する。コンポーネント資料は、対象実装の値がこの手順書より優先する。
4. ふるまいをPowerPoint内で疑似的に実装しない。ホバー、フォーカス、エラー、展開などは、独立した静的見本として示す。

## 2. 基本トークン

### フォント

| 用途 | 指定 |
| --- | --- |
| 本文・見出し | `Noto Sans JP` |
| 等幅表記 | `Noto Sans Mono` |
| テンプレートの本文色 | `#333333` |
| テンプレートの主見出し | `#000000` |
| 補足・フッター | `#666666` |

DADSの採用書体は`Noto Sans JP`と`Noto Sans Mono`である。既存テンプレートまたは対象環境がシステムフォントを使うことは公式DADSでは禁止されていないが、DADSの採用書体とは区別する。環境にNotoがない場合は、実際に使用するフォントを明記し、Notoを使用した・公式テンプレート準拠であるとは表記しない。

### 公式DADS適合の判定ゲート

- DADSは、Webサイト、Webアプリケーション、オンラインサービス、システムを主な対象とするデザインアセットである。DADSの色や書体を使っただけで、PowerPointが公式テンプレート準拠になるわけではない。
- 公式PowerPointテンプレート準拠と表記するには、配布元・版・利用条件を確認できる公式`.pptx`または明示的なPowerPoint向けブランドガイドを比較対象として入手し、対象資料と照合する。
- 上記の比較対象がない場合は、「DADSを参照して作成」「DADSの公開ガイドラインを参照」と表記する。「デジタル庁公式テンプレートそのもの」「完全準拠」とは表記しない。
- DADSの基盤は、サービスのニーズを考慮してスタイルを選択・変更することを認めている。変更した場合は、使用トークン、書体、可読性、アクセシビリティの判断根拠を資料または作成報告に残す。
- 根拠は、[基本デザイン](https://design.digital.go.jp/dads/foundations/)、[タイポグラフィ](https://design.digital.go.jp/dads/foundations/typography/)、[カラー](https://design.digital.go.jp/dads/foundations/color/)を優先する。ローカル実装と公式資料の版差がある場合は、使用した版と判断を明記する。

### 色

一般資料の主要色は次の値を使用する。全階調は [dads-color-palette.md](dads-color-palette.md) を参照する。コンポーネント再現では、対象コンポーネントのTailwindクラスが参照するトークンの解決済み値を使用する。

| 用途 | トークン | 値 |
| --- | --- | --- |
| 基調の濃紺 | `--color-key-1000` | `#00118F` |
| ブランドブルー | `--color-key-800` | `#0031D8` |
| 淡い青の文字 | `--color-key-50` | `#E8F1FE` |
| 注意のアクセント | `--color-primitive-yellow-300` | `#FFD43D` |
| 背景グレー | `--color-neutral-solid-gray-50` | `#F2F2F2` |
| 罫線グレー | `--color-neutral-solid-gray-200` | `#CCCCCC` |
| 本文 | `--color-neutral-solid-gray-800` | `#333333` |
| 白 | `--color-neutral-white` | `#FFFFFF` |
| 黒 | `--color-neutral-black` | `#000000` |

色は意味と併用する。成功・警告・エラーを色だけで区別しない。状態名、アイコン、説明テキストを必ず加える。

### フォーカス

フォーカス状態の静的見本は、React実装（`focus-visible:` バリアント）に合わせて次を使う。

- 黒の4pxアウトライン
- アウトラインから2pxのオフセット
- 外側に黄色300（`#FFD43D`）の2pxリング
- 角丸は対象コンポーネントの値（例: ボタンは8px）

## 3. スライド共通レイアウト

テンプレートは16:9（13.333 x 7.5インチ）である。ユーザー指定がなければこのサイズを使用する。

| 要素 | 既定値 |
| --- | --- |
| 左右余白 | 0.5インチ |
| セクションラベル | 8.5pt、太字、字間1.2pt、ブランドブルー |
| スライドタイトル | 27pt、太字、黒 |
| 本文 | 15pt、濃いグレー |
| カードタイトル | 14pt、太字、黒 |
| カード本文 | 10.5pt、濃いグレー |
| 補足 | 9.5pt、グレー |
| フッター | 7.5pt、グレー、字間1pt |
| フッター罫線 | グレー200、0.6pt |

テキストボックスは図形と揃えるときに余白を`0`にする。テキストが収まらない場合は、文字を縮小せず、短縮または分割する。

## 4. スライドスタイルの必須規則

### 情報設計

- 1スライドにつき結論は1つにする。タイトルは話題ではなく、読み手に伝える結論を表す。
- 本文は、結論を補強する根拠・データ・画面・コンポーネント見本だけを置く。装飾目的だけの図形やアイコンは置かない。
- 表紙、セクション区切り、クロージングは濃色背景で資料の区切りを作る。本文、比較、プロセス、表、コンポーネント見本は白背景を既定とする。
- 白背景のスライドでは、ブランドブルーを「区分・要点・操作の強調」に限定する。大面積の塗りつぶしや複数のアクセント色を同時に使わない。
- 重要な数値や結論は、本文を太字や色で過剰に装飾せず、十分なサイズ差・余白・位置で優先度を示す。

### グリッドと余白

| 項目 | 規則 |
| --- | --- |
| スライド外側 | 左右0.5インチ以上、上下も同等以上の余白を確保する |
| 基本間隔 | 0.3インチまたは0.5インチを基本単位として繰り返す |
| テキストと図形 | テキストボックスの内側余白を0にする場合も、図形との間隔は0.25インチ以上取る |
| カラム | 2カラムは左を主張、右を視覚資料とし、中央の境界を揃える |
| カード | 同じ列のカードは幅、高さ、見出し位置、本文開始位置を揃える |
| フッター | 本文領域と分離し、横罫線より下へ配置する |

コンテンツが収まらないときは、余白を削らず、文字を小さくせず、スライドを分ける。

### タイポグラフィ階層

| 階層 | 使用場面 | スタイル |
| --- | --- | --- |
| H1 | 表紙・結論・セクション | 33–35pt、太字 |
| H2 | 本文スライドのタイトル | 27pt、太字 |
| H3 | 要点見出し・カード見出し | 14pt、太字 |
| Body | 根拠・説明 | 15pt、通常 |
| Supporting | 補足・出典・キャプション | 9.5–10.5pt、通常 |
| Footer | スライド番号・資料種別 | 7.5pt、通常または太字 |

- タイトル、本文、注記の役割を同じ文字サイズやウェイトにしない。
- 本文を中央揃えにしない。中央揃えは表紙、セクション番号、短いラベルに限る。
- 日本語の長文を狭いテキストボックスへ詰め込まない。箇条書きより、短い見出しと段落または図表を優先する。

### 投影・研修資料の可読性

- 作成済みPPTXの実フォントを確認し、指定した`Noto Sans JP`が利用できない場合にMeiryoなどへ暗黙に置換されていないことを確認する。
- 研修会場・プロジェクターで読む本文は14–16pt以上を既定にする。11–12ptは本文、カード本文、図表ラベルに使わない。
- 10.5pt以下は、出典やページ番号など、投影中に読ませない補助情報に限る。補助情報もスライド目的に必要なら、本文サイズへ上げるか別スライドへ移す。
- タイトル、セクション見出し、本文、注記の4階層に絞る。近接した多数の文字サイズを混在させない。

### コントラストの実測

- 使用色がDADSトークンであっても、背景との組み合わせごとにWCAGコントラスト比を確認する。
- テキストは背景に対して4.5:1以上、罫線・ディバイダー・アイコンなどの非テキスト要素は隣接背景に対して3:1以上を満たす。
- `#E8F1FE`のような淡色背景上で`#666666`の小さい文字を使わない。投影用途では、本文を`#333333`以上の濃さにし、十分な文字サイズを確保する。
- 色以外の番号、見出し、位置、アイコンを使って意味を示す。ただし、これらは低コントラストの文字を正当化する理由にはならない。

### マスターレイアウト

- 更新・共同編集を前提とするPowerPointでは、繰り返し使う要素を個別配置せず、スライドマスターまたはレイアウトとして定義する。
- 最低限、表紙、セクション区切り、説明、比較、演習・ワーク、クロージングのレイアウトを用意する。
- タイトル位置、本文領域、フッター、ページ番号、背景色、余白はレイアウト側で固定する。各スライドで手作業の微調整を繰り返さない。
- スライドマスターを生成できないツールを使う場合は、同一座標・同一スタイルの再利用可能な生成関数を用意し、マスター未使用であることを成果物の注記に残す。

### DADS準拠の表記

- React版DADSのトークンと実装に基づいて作成した資料は「DADS準拠」または「DADSを参照」と表記する。
- デジタル庁の公式PowerPointテンプレート、ブランドガイドライン、最新版コンポーネントとの照合を完了していない限り、「公式テンプレートそのもの」または「完全準拠」と断定しない。

### 図表・表・UI見本

- 図表は1つの問いに答えるデータだけを表示し、単位・期間・出典を近接配置する。
- 表は比較軸を左端、数値を右寄せ、説明を左寄せにする。罫線はグレー200を使用し、塗り分けは必要な行・列だけにする。
- UI見本は実装由来の余白、色、罫線、角丸、状態を保持する。一般資料のカード表現で置き換えない。
- 画面キャプチャは切り抜き比率を変えず、枠線または淡いグレー背景で本文と区別する。
- アイコンや画像は、本文の意味を補う場合だけに使用し、説明なしの装飾画像を置かない。

### レイアウトの選択

| 内容 | 使用する標準レイアウト |
| --- | --- |
| 資料の目的・対象・作成者 | 表紙 |
| 章の開始・論点の切替 | セクション区切り |
| 結論と根拠、説明と画面・図表 | 本文と図表の2カラム |
| 同じ評価軸での3案比較 | 3カード比較 |
| 利用手順、導入手順、作業の流れ | 4ステッププロセス |
| 決定事項、担当、期限、次の行動 | クロージング |

同じレイアウトを連続して使わない。ただし、比較対象を同じ軸で反復する必要がある場合は例外とし、カードや図表の位置を固定して比較可能にする。

### 禁止事項

- タイトル下に装飾目的のアクセント線を引かない。
- グラデーション、影、角丸、色を、実装またはこの手順書に定義されない見た目として追加しない。
- 低コントラストの淡色文字、背景と区別できない罫線、意味を持たない小さな文字を使わない。
- 1スライドに複数の強調色、複数の見出しスタイル、複数の異なるカード形状を混在させない。
- テキストのみのスライドにしない。根拠となる図表、UI見本、プロセス、数値、または十分に構造化された比較を置く。
- ロゴ、アイコン、画面キャプチャを伸縮して縦横比を変えない。

## 5. リポジトリ実装から導く変換規則

### モバイルファーストと表示幅

- コンポーネント資料では、まずモバイルの基本スタイルを示し、`md:` バリアント（768px、モバイルファーストのTailwind規則）で変わる内容をデスクトップ見本として別に示す。コンテナクエリ（`@md:` 等）を使うコンポーネントは、コンテナ幅の前提を明記する。
- 見本には対象幅を明記する。実装比較が必要な場合の標準幅は、モバイル390px、デスクトップ1440pxとする。
- ホバー状態はポインターデバイス向けの見た目である。モバイル見本にホバー状態を混在させず、必要な場合は「ホバー対応環境」の独立した状態見本にする。
- アニメーションはPowerPointで再生したように見せない。`prefers-reduced-motion` の対象となる動きは、開始・完了状態と「動きは実装で確認」の注記で示す。

### 実装値の変換

- UIコンポーネントの寸法、余白、角丸、罫線は、対象コンポーネントの `.tsx` に定義されたTailwindクラスの計算値をそのままPowerPointへ換算する。一般資料のカード規則で置き換えない。
- このリポジトリのTailwindスペーシングは1単位4px（`px-4` = 16px、`py-3` = 12px、`min-h-14` = 56px）、`rounded-8` = 8px のように数値そのままのクラスも使われる。`rem` は16px基準で解決し、PowerPointでは `1 CSS px = 0.75pt` として換算する。罫線のpx値も同じ基準で扱う。
- 任意値クラス（例: `min-w-[calc(136/16*1rem)]`、`focus-visible:ring-[calc(2/16*1rem)]`）はcalc式を解決してから換算する。
- `border-radius` と `box-shadow` は固定の共通値ではない。対象コンポーネントの値だけを使う。影は `--elevation-1` から `--elevation-8` のいずれかで定義される場合だけ再現する（`shadow-*` クラスの実値は tailwind-theme-plugin の定義で確認する）。
- 画像・カード・アイコンのアスペクト比は変更しない。コンポーネントの `assets/` 内の画像は元の比率と寸法関係を保つ。
- 一般資料は、白背景・グレー200の罫線・グレー50のカード背景を基本とし、影や大きな角丸を装飾のために追加しない。

### 状態を持つUIの静的表現

- 状態は1つの図形の色変更だけで省略せず、通常・ホバー・アクティブ・フォーカス・無効・読み取り専用・エラーなど、実装される状態ごとに個別の見本を作る。状態の一次情報は `.tsx` 内のTailwindバリアント（`hover:`、`active:`、`focus-visible:`、`aria-disabled:`、`aria-[invalid=true]:`、`read-only:`、`data-[...]:`、`forced-colors:` 等）である。
- 各見本に状態名を付ける。PowerPoint上でクリックや入力ができるように見せかけない。
- フォーカスは黒4pxアウトライン、2pxオフセット、黄色300の2pxリングを保持する。
- 無効状態は色だけでなく、状態名と説明で識別する。このリポジトリでは `disabled` 属性ではなく `aria-disabled` を使う実装が多い点に注意する。`forced-colors:` バリアントが実装される場合は、PowerPointでは「強制カラーモードではシステム色へ置換」と注記する。
- `aria-invalid="true"` に対応する入力は、実装どおりエラー1（`#EC0000`）の罫線とエラーテキストをセットで示す。
- 読み取り専用入力は、実装どおり破線の罫線（`read-only:border-dashed`）として示す。

### ボタン・入力の実装見本

コンポーネント資料でButtonまたはInputを扱う場合は、次の実装値を基準にする（`src/components/Button/Button.tsx`、`src/components/Input/Input.tsx`）。別のコンポーネントへ流用しない。実装が変わった場合はソースを優先する。

| 要素 | 実装規則 |
| --- | --- |
| Solid-fill button | Key 900を通常色、Key 1000をホバー、Key 1200をアクティブにし、白文字を使う |
| Outline button | 1pxの`currentcolor`罫線、白背景、Key 900の文字を使う |
| Text button | 背景なし、下線付き。ホバー時はKey 50、アクティブ時はKey 100の背景を使う |
| Button size | lg: 136×56px、md: 96×48px、sm: 80×36px、xs: 72×28px。sm・xsも44pxの操作領域を持つ |
| Text input | 1pxグレー600罫線、白背景、8px角丸、左右16px・上下12pxのパディング |
| Text input size | sm: 40px、md: 48px、lg: 56pxの高さ |

### コンテンツとセマンティクス

- ラベル、入力欄、補足、エラー文、ボタンは実装の読順と関係を保って配置する。PowerPointの図形を視覚的な都合だけで並べ替えない。
- 表示テキストは画像化せず、編集可能なテキストとして配置する。多言語化のため、言語依存の情報を図形の装飾やスクリプトに埋め込まない。
- 画像、SVG、アイコンを使う場合は、意味を説明する代替テキストを設定する。情報を持たない装飾画像は代替テキストを空にする。
- ネイティブHTML・ARIA・react-aria-componentsが担う操作・読み上げ・キーボード挙動は、静的資料に偽装しない。必要なら「実装での操作・読み上げ要件」として注記する。
